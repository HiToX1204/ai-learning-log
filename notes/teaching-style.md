# 讲解方式偏好（给以后的我）

> 用途：每次开始讲新概念前先读一眼，避免重复踩"讲不清"的坑。
> 来源：实际对话中本人明确说过"懂了"和"还是不懂"的对照。

## 有效的形式（优先用）

0. **数学公式用 LaTeX**（GUI 能正常渲染），不要用 `Σᵢ`、`·`、`↕` 这类组合字符——等宽字体下会糊成一团。
   - 差：`∂loss/∂w = (1/n)·Σᵢ 2(predᵢ - yᵢ)·xᵢ`
   - 好：`$\frac{\partial L}{\partial w} = \frac{1}{n}\sum_i 2(p_i - y_i)x_i$`
   - 推导要**一步一行**，每行只做一个变换

1. **先画图，再上代码。** 尤其是 DAG / 数据流 / 依赖关系，用 ASCII 图画出节点和箭头，比文字描述快得多。
   - 例：`x,y → e → f → d`，把"`e` 有两条下游路径"画出来，一个图就解释了为什么顺序重要。

2. **用生活化的"记账/分账"比喻封装数学。**
   - 例：把梯度反向传播讲成"总账单 1 块钱，按比例往上游分；一个中间件要为两个成品部件负责，必须等两笔账都到齐才能结算"。
   - 效果：比"链式法则 + 拓扑序"这类术语直接讲清楚得多。

3. **具体数值走一遍，带状态表格。**
   - 例：`x=2,y=3,z=1` 一路算下来，每次调用后打一张 `(x,y,z,e,f,d)` 的 grad 表，标出"★ 关键跳变"。
   - 关键：**每一步都给出"调用前后数值怎么变"**，不要跳过中间态。

4. **时间轴对比正确/错误顺序。**
   - 例：把前序和后序画成两条时间线，标出"e 结算"和"f 转账"的先后，错因一眼可见。

5. **先承认自己估错/说错。**
   - 例：时间点估错（`_backward` 在 1:10 而非 45 分钟）、断言 CSV 会丢 bool（实测不成立）。
   - 直接更正比含糊带过更可信。

## 无效的形式（避免）

1. **只有术语和抽象描述**：如"后序遍历保证拓扑序"——听不懂。
2. **只给结论不给过程**：如"用 `+=` 因为要累加"——不如给两组数字对比。
3. **一次铺开多个任务**：会明确要求"一次一步、逐步反馈"。
4. **假定经验**："我记得是这样"式的断言必须先用代码验证再说。
5. **长篇大论**：问一个参数就答一个参数，不要附带三页背景。

## 本人的纠错习惯（值得记住）

- 会主动指出"你没讲清楚"、"你说错了"、"我不想不求甚解"。
- 会要求删掉不合适的内容（如"明天接什么"、"自测"不进笔记）。
- 会纠正格式问题（日志要写"模块 + 具体知识"，不要堆裸名词）。
- 这些纠正**都是对的**，应当照办而不是解释。

## 一句话

> **能画图就别写字；能给数字就别给形容词；能走一遍就别讲一遍。**

## 补充（2026-11-23，线代课讲砸之后）

### 一条消息只推一步，回「过」才继续

- 触发场景：11-23 讲矩阵，一条消息里塞了「点怎么搬 + 为什么四点决定整块 + 形状 + 面积倍数」，直接换来"完全不能理解"。
- 改法：一条消息 = **一个事实 + 一个十秒钟内能答完的问题**；对方回"过/不懂"，不懂就把这一步再拆。
- 实测：同一个矩阵、同一套符号，改成一句一停后全程没再卡。
- 判断粒度是否合适的信号：对方连续两次回"没问题"→ 可以提速一档；对方开始复述/提问 → 说明这层落地了。

### 新词先给生活锚点，再给矩阵语言

- 顺序反了会全军覆没。**权重**先讲"总评 $=0.3$ 平时 $+0.7$ 期末，$0.3$ 就是权重（占几成）"，等这个数落地了，再说是"矩阵的一行"。
- 反例：先给 $W$、$\top$、$(4,2)$ 再解释"权重是什么"→ 每个字都认识，合起来是天书。

### 不要假定某种"视觉直觉"已经存在

- "平面 = 一堆点的集合"、"方格被压成平行四边形"这类视角，是 3b1b 那条路的前提，**需要成本去建**。
- 一旦对方在那条路上卡住，先撤掉它旁边最贵的东西（这次撤掉了 det 与面积），保住主干（点怎么搬、数怎么算）。
- 修辞判据：如果一句话的正确性依赖"你能想象出一个图形"，那它就是高风险句。

### 讲砸了就明确说"这段作废"，不要修补

- 明确列出"我错在哪 1/2/3"，再说换成什么。对方要的是"你知道自己错在哪"，不是道歉。

### 出现新词汇必须先定义，不许当作已会

- 2026-11-24 原话："以后这种出现新的词汇时你都要告诉我"。
- 我在讲 `xor_nn.py` 时直接用了 `weight`、`parameter`、`属性`、`对象` 这些词，默认他会，实际不会。
- 规则：**任何第一次出现的词（英文标识符、API 名、术语），先给一句"它是什么、长什么样、在代码里怎么出现"，再往下讲。**
- 判断标准：能说出它在屏幕上长什么样（形状、几个数、带不带括号），才算定义清楚。
- 另注：**数学水平提高 ≠ 能看代码**。这两件事要分开评估，不能因为刚讲完矩阵就假定他能读 PyTorch 代码。

### 不许让人"盲人摸象"：先亮参数卡，再出题

- 2026-11-24 原话："以后你一定要把参数含义先说清楚，不要让我盲人摸象……你不要总是让我去猜一些我没学过的东西。"
- **事故复盘**：`nn.Linear(5, 2)` 的参数顺序我从未讲过，却让他预测 `weight` 形状。他答 $(5,2)$——这正是"输入在前"的直觉，来自他自己写的 `xor_mlp.py`。**没给规则就出题 = 制造挫败。**
- **三条硬规矩**：
  1. 任何新 API 第一次出现，先给一张卡：**参数（位置/名字/含义）+ 关键属性形状 + 一个真实输出例子**。卡统一放在 `notes/glossary.md`。
  2. 出题只考"**已给的规则 + 换新数字**"。凡是需要他先猜一条没讲过的规则，都是我越界。
  3. 判断标准：如果答错不能唯一归因于"数学没懂"，那这题就不该出。
  4. **缩写不许裸用**：MSE / SGD / BCE / ReLU / lr 这类，第一次出现必须展开英文全称 + 中文 + 一句话定义。2026-11-24 我用 MSE 下结论用了整整一节，他才知道"你都没解释"——这跟直接扔公式没区别。


### 收尾即写笔记，不留到第二天

- 2026-11-24 原话："笔记你更新了没有，不要每天都要我提醒"。
- 事故：11-24 的笔记只写到 11:00 的 M2，当天下午的 `xor_nn` 走查、MSE、二维分类四步实验、进度对账**全没进档案**，第二天才发现。
- 规则：**每次会话结束（他说"收工/继续/明天"之前）无条件更新四处**——`notes/YYYY-MM-DD.md`、`logs/2026-MM.md` 一行、`logs/PROGRESS.md` 当前阶段、必要时 `notes/teaching-style.md`。
- 判据：如果当天有新脚本或新图，笔记里必须出现它们的路径与关键数字。

### 讲代码：先讲它验证什么，再讲那几行，最后才是打印

- 11-24 翻车：我把 `m2_lr_limit.py` 逐行讲了一遍"这行在干嘛"，换来第二次"你讲的不太好"。他要的是**这个文件为什么存在**。
- 正确顺序：**① 它要验证哪一句结论 → ② 剥掉排版后真正做数学的那 1–3 行 → ③ 输出怎么读 → ④ 剩下的 print/f-string 一句话带过。**
- 判据：一个 58 行的脚本，如果我说不出"删掉它你会失去什么"，那说明我自己也没抓住它的目的。
- 顺带的信号：**对方问"目的是什么"时，往往是他脑子里缺一个前置概念**（这次是"学习率"），不是缺代码讲解。先确认前置概念，再讲代码。

### 对方忘了旧概念，说明卡点在地基不在新内容

- 11-24 讲到一半他说"学习率是什么我忘记了"。此时不该继续推新推导，应立刻退回最朴素锚点（学习率 = 步幅），用他**自己做过的那组数**（$\eta=0.1/0.5/1.1$）重新落地，再往前走。
- 他愿意说"听不懂，可以放过吗"时，**就真的放过**，只留一句能用的结论。
